# 代码注释规范

> 本规范由项目作者书写，未经允许不得随意改动。

## 判断标准

注释要回答一个从代码看不出来的问题：为什么这样做、谁负责这件事、哪些状态不能破坏、
兼容分支什么时候生效。删掉以后仍能从代码得出同样结论的，就删掉或缩短。

## 保留

- 职责和所有权边界：哪个模块负责什么，谁生成、谁消费。
- 维护约束：索引、顺序、坐标系、单位、缓存失效、脏标记。例如「条目按文件顺序求值，组计数由写入器推导」
  「Blender 的 pose 缩放是相对静止缩放的比值」。
- 跨模块契约：`jcns_drivers._CHANNELS` 里读法元组的格式、驱动器变量的顺序。
- 兼容分支的触发条件：哪个文件版本、哪种字段取值会走这条路。
- 生命周期要求：什么时候注册、什么时候重建、什么时候必须清掉。

## 删除

日期、版本历史、提交号、样本来源、覆盖数量、验证过程（「第 N 轮实测」「误差 0.001°」）、
旧实现的叙述、逐行复述代码、与悬停提示重复的解释、面向 AI 的辩解措辞。

引擎行为的**结论**可以留在注释里（它就是维护约束）；得出结论的**过程和证据**
写进 `scripts/probes/README.md` 或 `modules/jcns_parser.py` 的字段说明。

## 措辞

- 用准确的陈述句，不写「应该没问题」「理论上」。
- 说真实的粒度，不凭空加「只有这里才能……」。
- 拿不准的格式事实，先确认，或者移到调查文档里。

## Docstring

- 模块 docstring 写稳定的职责和少量全局约束，不写 API 清单。
- 函数 docstring 只在签名说不清时补充：参数的单位、返回值的形状、调用前提。

## 工作规则

- 修缮注释时，改完必须更短，而且不能动逻辑。
- 用 `python tools/check_no_logic_change.py <文件>...` 自证：它对比工作区和 `HEAD`（或 `--base <提交>`），
  去掉注释和 docstring 后比较 AST，逻辑有任何变化就失败。
- 再跑 `python -m py_compile <文件>` 和 `git diff --check`。
- 注释修缮单独提交，不和逻辑改动混在一起。
